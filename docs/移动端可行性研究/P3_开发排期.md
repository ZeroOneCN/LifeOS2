## 1. 本轮：release 体积实测（只测量，不分发）

> **签名说明**：release 沿用 `android/app/build.gradle.kts` 里的 debug keystore；本轮**不生成正式签名、不上传、不发布**。
> **此包仅用于体积测量，不可分发。**

构建命令（Windows PowerShell）：

```powershell
$env:GRADLE_USER_HOME='C:\Temp\gradle-probe-home'
& 'C:\Env\flutter\bin\flutter.bat' build apk --release                 # 291.3s
& 'C:\Env\flutter\bin\flutter.bat' build apk --release --split-per-abi # 76.6s
```

实测产物（`mobile/build/app/outputs/flutter-apk/`，仅留本地，未提交）：

| 产物 | 字节 | 显示 MB | 说明 |
|---|---:|---:|---|
| `app-release.apk`（通用） | 58,559,024 | 55.85 | 内置 3 套 ABI 的 Flutter 引擎 |
| `app-arm64-v8a-release.apk` | 20,432,322 | 19.49 | 真机推荐分发口径 |
| `app-armeabi-v7a-release.apk` | 17,966,366 | 17.13 | 老设备 |
| `app-x86_64-release.apk` | 21,923,786 | 20.91 | 模拟器 |
| `app-debug.apk`（当前） | 211,950,219 | 202.13 | 未拆分 + JIT 引擎 + 新增插件 |
| debug 基线（P1 记录） | 171,839,258 | 163.9 | 本文件原对比基准 |

对比与预估：

- 通用 release 为当前 debug 的 **27.6%**（降 72.4%）；相对 P1 基线 163.9 MB 为 **34.1%**。
- arm64 拆分包为当前 debug 的 **9.6%**（降 90.4%）；相对 P1 基线为 **11.9%**。
- 原方案预估「拆分 12–18 MB / 通用 25 MB」：
  - `armeabi-v7a` 17.13 MB 在区间内；
  - `arm64-v8a` 19.49 MB **超出上限 1.49 MB（+8.3%）**；
  - `x86_64` 20.91 MB 超出 2.91 MB；
  - 通用包 55.85 MB 是 25 MB 预估的 **2.23 倍**。
- **结论：拆分包接近预估但 arm64 略超；通用包预估不成立。** 分发应按 arm64 拆分或 AAB，不能按 25 MB 规划通用包。
- 通用包偏大的主因：内置 3 套 Flutter 引擎原生库 + 全量资源；本轮新增 `share_plus`、`path_provider` 也带来少量原生代码。
- debug 从 P1 的 163.9 MB 增到 202.1 MB，属于 debug 口径（未拆分 + JIT），不能代表分发体积。

### 1.5.2 步数对账：到底是哪一环错了

先对账后改码。原始数据（2026-11-07 10:05，后端 9515 + 真实 MySQL）：

| 来源 | 今日/最新 | 30 天汇总 | 备注 |
|---|---|---|---|
| `GET /health/steps?start=2026-11-07&end=2026-11-07` | 08-09=0、09-10=507、10-11=507 | — | 当天 3 条，均 10:05 写入 |
| `GET /health/steps/stats?days=30` | trend 07 日 = **507** | total **123,005** / avg **4,100** / max **12,352** | 每日取当天最大值（分时段是累计序列） |
| `GET /health/overview` | `latest_steps.steps = 507`，日期 2026-11-07 | `week_summary.steps_avg = **1,385**` | 按**记录条数**平均，不是按天 |
| App 步数统计页 | 明细最后一天 07 | 123,005 / 4,100 / 12,352 | **与后端一致** |
| App 健康中心 | 「今日 **507** 步」、「日均 **1,385**」 | — | 读的是总览快照 |

结论（三问三答）：

1. **App 的数据是不是旧的？** 步数统计页不是（进页即请求，数字与接口一致）；健康中心是——总览只在登录后拉一次，切 Tab 不重新请求，页面常驻 `IndexedStack`，所以停在启动时的快照。
2. **是接口旧、App 缓存，还是 App 算错？** 接口不旧、也没有端上缓存；是 **App 没有重新拉取**，外加两处口径错误。
3. **今天有没有数据、最后一天是哪天、切页是否重请求？** 今天有 3 条（最新 507）；统计页最后一天 07；统计页每次进入都请求，健康中心之前不会。

两处口径错误：

- 「今日 X 步」实际取 `overview.latest_steps`，没有比对日期——最新记录不是今天时也会写「今日」。
- 「日均步数」取 `week_summary.steps_avg`（1,385，按记录条数平均）；按天取最大值后平均才是 2,376（`stats?days=7`）。

修复（`1c213c6`）：切 Tab / 点右上刷新都会重拉总览；「今日」只在日期匹配时使用，否则显示「最近 MM-dd」；7 日均改用 `/health/steps/stats?days=7` 的 `avg_steps`，失败显示「—」而不展示错误口径。

### 1.5.3 步数新增（`1c213c6`）

- 入口：健康中心 → 步数统计 → 右下「新增步数」。
- 字段与网页端一致：`record_date` / `period` / `steps`；距离与消耗由后端按步幅计算（默认 70cm、0.04 kcal/步）。
- 时间段以当前小时为默认（与网页 `periodForNow()` 一致）；同日期同时段提交返回 409，表单内提示并保留输入。
- 在线提交、不入离线队列：录完要立刻看到汇总；该接口没有幂等键，入队重试可能重复入库。
- 保存成功 → 返回步数统计页并立即重拉：实测总步数 123,005 → **123,732**（当天取最大值 507 → 1,234，+727），记录数 496 → 497；页面无需手动刷新。

### 1.5.4 用药新增与打卡入口（`abb7ec0`）

- 之前的问题：打卡入口只在「记录详情页」里，列表没有任何按钮，用户找不到；创建入口完全没有。
- 新增：用药跟踪页右下「新增用药」、健康中心「今日用药待办」右上「新增」。

### 1.6.1 通知角标与乱码（`8fe6845`）

**角标不刷新**：五个 Tab 根页各自 `new NotificationBell` 并各自拉一次 `stats`，在通知中心读掉后只有当前实例更新，
其余 Tab 常驻 `IndexedStack` 仍停在旧值。修复：

- 新增 `NotificationUnreadController`（`ChangeNotifier`），由 `AppScope` 注入，五个铃铛共用同一份计数；
- 通知中心读到 stats / 单条已读 / 全部已读时直接 `setCount`，本地即可见；
- 铃铛从通知中心返回后再 `refresh()`，以 `/notifications/stats?days=365` 兜底校正；
- 登出清零，登录后自动拉取。

**乱码**：全库 86 条通知逐条扫描，**仅 id=92** 异常（2026-11-07，来源 `finance_loan_due:574`），标题与正文同时坏。
原始证据：

| 项 | 值 |
|---|---|
| title 前 12 字节 | `c3 a3 c2 80 c2 90 c3 a7 c2 bd c2 91 c3 a8 c2 b4 c2 b7` |
| content 前 12 字节 | `c3 a5 c2 b9 c2 b3 c3 a5 c2 8f c2 b0 c3 a3 c2 80 c2 8c c3 a8 c2 8a c2 b1` |
| Python repr(title) | `'ã\x80\x90ç½\x91è´·è¿\x98æ¬¾ã\x80\x91è\x8a±å\x91\x972 2026'` |

判断：字节形如 `C3 A3 C2 80 C2 90`，即「已按 latin-1 解出的 `ã U+0080 U+0090`」又被 UTF-8 编码一次；
`latin-1` 解码后再按 UTF-8 解码可还原「【网贷还款】花呗2 2026…」。
其余 85 条中文正常，App 统一按 UTF-8 解析、没有二次编码 → **后端入库时已是坏的，App 解码无误**。
按边界只报告不改；影响范围仅 `id=92`（若后端修复，需重存该行或做一次 `encode('latin-1').decode('utf-8')` 迁移）。

## 4. 需要你拍板

### 4.1 release 签名与分发方式（未定）

- **问题**：当前 release 用 debug keystore 签名，只能用于体积测量；正式 keystore、包名与分发方式未定。
- **影响**：包不能交付给任何人；后续换签名会导致覆盖安装失败、已装用户需卸载重装。
- **建议修法**：确定正式 keystore（离线保存、不入库）与 `applicationId`；选择侧载 / AAB / 应用市场；签名后出 arm64 拆分或 AAB；同步确定版本号与升级策略。

### 4.2 后端缺幂等键（离线队列重复防护是补偿，不是真幂等）

- **问题**：`POST /finance/shopping/records`、`POST /investment/forex` 没有 `Idempotency-Key`；客户端只在重试时按字段查重。
- **影响**：①首次请求已写入但响应超时——重试查重可挡住；②并发/多设备在「查重」与「写入」之间插入同记录——仍会重复；③同日同品种同方向同价同量同盈亏的两笔真实交易，第二笔重试会被误判「已写入」而**漏写**；④后端补默认字段导致查重不命中——仍会重复。用药打卡用 PUT，幂等但可能覆盖其他端同期更新。
- **建议修法**：后端给创建类接口加幂等键（独立幂等表或唯一约束，同键返回首次结果），客户端用 `localId`/UUID 作键；打卡改为按「药物 + 日期 + 时段」条件更新；上线后删除客户端字段查重。

### 4.3 后端时间口径不一致（会话时间差 8 小时）

- **问题**：会话 `created_at` 由 MySQL `NOW()` 写入（服务器本地时间），`last_used_at` 刷新时写 UTC；同一条记录可相差 8 小时。
- **影响**：登录设备的「最近活跃 / 登录于」可能失真，用户无法判断异常登录；未来安全审计同样不可信。
- **建议修法**：后端统一 UTC 存储（`datetime.now(timezone.utc)` 或 MySQL `time_zone='+00:00'`），出参带时区/ISO Z；旧数据按已知规则校正；移动端改为 UTC 解析后 `toLocal()` 展示。

### 4.4 报告原始 id 未翻译与「平均亏损 +11.69」

- **问题**：财务/投资报告表格里的「平台」仍是 `platform_id`（1/2/3）；「平均亏损 +11.69」是后端按绝对值返回并加 `+`。
- **影响**：用户看不懂平台编号；亏损带正号容易被读成盈利。**网页端同样存在，不是移动端独有。**
- **建议修法**：在后端报告生成处映射平台名并按财务语义输出负数或注明「亏损」，网页与移动端共用同一口径；若只改移动端字典映射，会与网页显示不一致，不建议。

### 4.5 体检 eGFR 单位被截断

- **问题**：真实库 `unit` 为 `mL/(min*1.`（长度 10），接口原样返回；正确应为 `mL/(min*1.73m²)`。
- **影响**：医学单位不完整，体检页与报告都显示误导；所有端一致受影响。
- **建议修法**：修数据库字段值并排查写入端截断原因（字段长度/导入脚本）；移动端无需改代码，重新拉取即恢复。

### 4.6 投资域接口 640ms 偏慢

- **问题**：投资总览接口优化后仍需约 640ms（其他域 60–160ms）；页面已异步不阻塞导航，但数据到屏仍慢。
- **影响**：冷启动/弱网下投资 Tab 首屏慢；不影响其他 Tab。
- **建议修法**：抓后端慢 SQL，检查聚合与索引；把总览拆成「首屏必需 + 次要指标延迟加载/缓存」；目标 <300ms。移动端已按域并发，后端变快后自动受益。

### 7.1 网贷账单数据范围与「全部账单」分页修复（2026-11-07）

**事实基线（勿再误判）**：`finance_loan_bills`（用户 1）的 `bill_month` 真实覆盖 **2023-01 ~ 2028-08，共 68 个月、347 条**，其中 **2026-12 ~ 2028-08 为真实存在的未来月份账单（70 条）**。早期以 App 可见范围倒推「库里只有 2025-04~2026-11」是错的：App 当时只加载到一部分，不代表后端数据只有这些。

**`bill_month` 原始格式**：数据库为 `Date`，JSON 序列化为 `2028-08-01`；App 只做 `substring(0,7)` 取标签，无 `DateTime.parse`、无时区偏移，标签不可能凭空造出 2027/2028。

**旧版为什么「打头是 2028-08、近期月份不见」**：
1. 后端 `crud_router` 列表默认 `bill_month` 倒序且**不过滤未来**，第 1 页（`page_size=100`）全是未来账单；
2. 多个并列 `SliverPersistentHeader(pinned:true) + SliverList` 布局导致长列表滚动冻结，只能看到前 20 个月，剩余月份（含未来块）根本滚不出来。

**修法**：
- 数据：拆两块并行取全量 —— 主块 `end=本月最后一天`（277 条，`2026-11 → 2023-01` 倒序）+ 未来块 `start=次月 1 日` 取完后整块反转（70 条，`2026-12 → 2028-08` 正序）拼在末尾；排序由后端 `bill_month` 决定，客户端只按数据顺序分组，不跨页重排。
- 布局：每组改为 `SliverMainAxisGroup[header, list]`，滚动冻结解除，68 个月全部可达。

**验收（逐月对照）**：后端 347 条 / 68 个月 = App 347 条 / 68 个月；月份集合完全一致；**68 个月条数逐月全部相等**（如 2026-11:8、2026-01:6、2023-01:2、2026-12:8、2028-08:1）；`distinctIds=347` 无重复；列表尾部「共 347 条 / 已加载全部」。住房、水电、订阅三个 Tab 同样按「未来月份排末尾」规则核对通过。

### 7.2 体重 / 体成分接入（2026-11-07）

**后端接口与字段**（`backend/app/api/routes/health/body.py`，表 `health_body`，用户 1 共 47 条、2026-04-13 ~ 2026-10-30）：

| 接口 | 说明 |
|---|---|
| `GET /health/body?page&page_size&start&end` | 列表，按 `record_date` 倒序，`total` 为过滤后总数 |
| `GET /health/body/{id}` | 单条（编辑预填兜底） |
| `POST /health/body` / `PUT /health/body/{id}` / `DELETE /health/body/{id}` | 新增 / 更新（`exclude_unset`，只改传入字段）/ 删除（204） |
| `GET /health/body/stats?days=0` | `latest`（BMI 缺失时按身高体重补算）、`trend`（全量按日期升序）、`avg/min/max_weight`、`record_count` |

字段：`record_date`（Date）、`gender`、`height_cm`(cm)、`weight_kg`(kg)、`bmi`、`body_fat_percent`/`muscle_percent` 等 15 项体成分(%)、5 项围度/长度(cm)、`note`；全部可空。

真实示例（id=51）：
```json
{"record_date": "2026-10-30", "height_cm": 173.0, "weight_kg": 74.7, "bmi": 25.0, "body_fat_percent": 22.3}
```
同一条记录的 `muscle_percent` 为 0（未采集）。

**「未采集」口径**：历史数据大量 `muscle_percent=0`（43 条）、`fat_mass_kg=0`，1 条 `height_cm=0`。移动端解析时统一把 0 归一成 null，展示「—」；录入表单也拦截 0（不允许把 0 写回库）。

**同一天重复录入**：网页端手动新增是 **POST 新增一条**（表无 `(user_id, record_date)` 唯一约束），只有蓝牙同步 `POST /health/body/blesync` 才覆盖当天；移动端保持一致，并在表单底部写明。

**已知后端缺陷（未改后端，只报告）**：`BodyRead` 直接继承 `BodyCreate`，`height_cm / weight_kg / bmi` 带 `gt=0` 响应校验；一旦某条历史记录 `height_cm=0`（实测仅 id=20 / 2026-06-12），**包含它的整页列表**都会 500（`page_size=27` 正常、`28` 起 500；`GET /health/body/20` 同样 500）。移动端改为「按 `start`/`end` 日期窗口取全量 + 500 时日期二分降级」，只跳过该日期，其它 46 条照常展示并在列表底部提示。修复建议：`BodyRead` 不要复用 `BodyCreate` 的 `gt=0`，改成 `ge=0` 或 `None` 放行。

**移动端实现**：健康首页「常用」新增「体重记录」卡片（摘要取 `/health/overview` 的 `latest_body`，如「最新 74.7 kg · 10-30」）；`/health/body` 页含概览（当前体重 / BMI / 体脂率 / 平均体重 + 区间）、体重趋势（点按或长按横向拖动逐日读数，与收益曲线同交互）、历史列表（日期倒序、行内体重 + BMI/体脂/肌肉，空值「—」）；`/health/body/new` 与 `/health/body/:id` 复用同一表单，编辑页「左保存右删除 + 删除二次确认」。BMI 在身高体重齐备时按 `w/h²` 保留 1 位小数随保存提交，身高清空时同步置空 BMI（避免陈旧值）。「记一笔」面板里的「体重」占位改为直达该录入页。

**实测**：新增 72.5 / 21.5% / 173cm → 概览 48 条、BMI 24.2、趋势末点 72.5；改 73.1 → BMI 24.4 同步；删除 → 回到 47 条、最新 74.7。`GET /health/overview` 在 POST 后立即反映新 `latest_body`（无 30s 缓存滞后），删除后回退。
