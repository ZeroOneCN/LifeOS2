# P4 全功能 CRUD 对照矩阵

> 更新：2026-11-07
> 范围：只读核对 `frontend/` 与 `mobile/`，本文件为唯一交付物；未改任何业务代码。
> 依据：`frontend/src/config/routes.ts` 为路由唯一真源；每条能力都回到页面源码里的 `api.*` 调用确认，不按页面标题推断。
> 移动端对应关系：`mobile/lib/core/router/app_router.dart` + `mobile/lib/features/**`。

---

## 0. 结论摘要

- 网页端共 **30 条路由条目**：**29 个页面** + 1 条旧链接重定向（`/user-center/settings` → `/user-center`，不参与能力对照）；通知中心另有 **5 个独立子面板**（渠道 / 提醒开关 / 邮件 / 模板 / 发送记录）。按页面内子 Tab 展开后，共 **42 个能力行**。
- 移动端现状（按 42 个网页端能力行计，移动端独有页另列于 2.5）：

| 档位 | 数量 | 含义 |
|---|---:|---|
| 完全实现 | 3 | 核心增删改查 + 特殊动作与网页端对齐 |
| 部分实现 | 14 | 页面可用，但缺一类或多类写操作 / 特殊动作 |
| 只读占位 | 11 | 页面存在，只能看，不能写 |
| 未建页面 | 14 | 移动端无入口、无页面 |

> 另有移动端独有页面 4 个（流水、记一笔支出、服务器地址、关于），其中 3 个为完全实现、1 个为部分实现。

- **移动端不是「页面不够」，而是「写操作不齐」**：录入入口集中在步数、用药、体重、账单、外汇，其余域多数只能查看。
- 最高优先级集中在 **每天都会产生数据、且错了必须能改** 的三处：购物/支出、用药、运动；其次是完全缺失的饮食记录与债务本体。
- 管理员后台类页面（活动日志、安全审计、系统设置、完整备份）建议**刻意不在移动端建**，只保留设备会话与备份导出；理由见第 6 节。

## 1. 判定口径

### 1.1 移动端档位

| 标记 | 档位 | 判定标准 |
|---|---|---|
| ✅ | 完全实现 | 列表 + 查询 + 新增 + 编辑 + 删除（该页面网页端具备的全部写操作）+ 特殊动作均已落地 |
| ◐ | 部分实现 | 有页面且至少有一类写操作，但缺编辑/删除/批量/导入导出等 |
| 👁 | 只读占位 | 页面存在，仅调用 GET，没有任何写入口 |
| ⛔ | 未建页面 | 移动端无路由、无页面 |

> 说明：用户要求的三档（完全实现 / 只读占位 / 未建页面）之外，必须单列 **部分实现**。否则「只能新增不能改」会被误记为完全实现，「只能看」又会被误记为部分实现，二者都不是事实。

### 1.2 优先级

按「录入频率 × 缺了是否影响日常使用」排序：

| 级别 | 含义 |
|---|---|
| P0 | 每天产生数据，缺失会直接迫使回网页端纠错 |
| P1 | 每周级高频，或该域核心写操作完全缺失 |
| P2 | 每月级，或低频但补录时必须有 |
| P3 | 低频 / 管理员后台 / 移动端刻意不建 |

## 4. 特殊动作缺口专题

| 特殊动作 | 网页端接口 | 移动端 | 影响 |
|---|---|---|---|
| 蓝牙体脂秤同步 | `POST /health/body/blesync` | ❌ | 无法用体脂秤一键写入当天体重与体成分 |
| 用药打卡 | `PUT /health/medication/{id}` | ✅（离线队列，幂等） | 已覆盖，且断网可用 |
| 网贷 / 民间借贷还款 | `POST /finance/repayments`、`POST /finance/debts/{id}/repay` | ✅（新增/编辑/删除） | 已覆盖，含优惠与实付 |
| 租房期次标记已付 / 改金额 / 改到期日 | `PUT /finance/rent-terms/{id}?paid=&amount=&due_date=` | ❌ | 房租付款状态只能回网页端维护 |
| 手机卡扣账 / 整月结算 / 充值 / 校准 | `POST /lifestyle/phone-cards/{id}/deduct`、`/settle`、`/recharge`、`/adjust` | ❌ | 月度话费与余额无法在手机端处理 |
| 购物 xlsx 导入 | `POST /finance/shopping/import` | ❌ | 批量购物账单只能网页导入 |
| 外汇 MT5 xlsx 导入 | `POST /investment/forex/import` | ❌ | 交易明细只能网页导入 |
| 数据导入 / 恢复 | `POST /backup/import` | ❌ | 手机只能导出，灾难恢复必须回网页端 |
| 定时备份 | `GET/POST/PUT/DELETE /backup/schedules`、`toggle` | ❌ | 无法在手机配置自动备份 |
| 物品批量编辑 / 购物同步 | `PUT /lifestyle/items/batch-update`、`POST /lifestyle/items/sync` | ❌ | 批量整理与自动建物品缺失 |
| 报告生成 / 导出 PDF | 四域 `POST .../reports/generate`、`GET .../export` | ❌ | 手机只能看已生成报告，不能产出 |
| 通知渠道 / 模板 / 提醒开关 / 测试发送 | `/notifications/channels`、`/templates`、`/settings`、`/test-send`、`/scan` | ❌ | 推送配置完全依赖网页端 |
| 下线其他所有设备 | `POST /auth/sessions/revoke-others` | ❌ | 只能逐台下线 |

## 6. 明确跳过与不建的理由

本矩阵**没有跳过任何业务路由**；以下页面虽列入表内，但建议移动端保持「不建」或「只做轻量入口」，理由写明：

| 页面 | 建议 | 理由 |
|---|---|---|
| `/home` | 不建跨域首页 | 移动端底部五 Tab 已承担域级入口；再造一个四域总看板会重复拉 4 个 overview，首屏成本高、信息密度低 |
| `/activity-logs` | 不建 | 管理员排障场景，需要宽表格、多条件筛选与批量清空，手机屏不适合；且普通账号无权限 |
| `/login-audit` | 不建 | 同上，安全审计属后台运维 |
| `/system-settings` | 不建 | 品牌 LOGO / 站点标题为一次性配置，误改影响全站；不应放在随身设备 |
| `/notifications` 五个子面板 | 暂不建 | 渠道密钥、SMTP、模板占位符属配置型操作，低频且易误配；先保证「收通知、标已读」这一条主线 |
| 四域「报告」的生成 / 导出 | 暂不建 | PDF 生成与下载在手机端可用，但报告是周期性复盘动作，移动端保留「查看已生成报告」即可；若后续要做，优先「生成 + 分享」，导出次之 |
| `/backup` 导入 / 定时任务 / 备份管理 | 暂不建 | 恢复导入是高危写操作，必须桌面端确认表范围与覆盖风险；手机只保留导出与日志查看 |
